# Reserve PRO

## 1. プロジェクト概要

Reserve PROは、歯科医院向けの予約管理デモアプリケーションです。
患者側の予約希望フォームと、管理側の予約枠・カレンダー管理機能を統合したシステムです。
医院での電話・LINE等を通じた予約希望のやり取りをシステム化し、患者様が迷わず予約できる導線と、管理側の予約枠調整の負担を減らすことを目的として作成されました。

## 2. 作成背景

本プロジェクトは以下の背景・目的からスタートしました。

- **予約希望の整理**: これまでバラバラに管理されがちだった予約希望のやり取りを整理・一元化したかった。
- **患者様目線の導線**: 患者側が迷わずスムーズに希望日時を選んで予約できる導線を作りたかった。
- **管理の効率化**: 管理側が不定休や時間帯ブロックなどを簡単にカレンダー上で調整できるようにしたかった。
- **迅速な検証**: まず動くデモを短期間で作ることを優先し、実際の操作感や運用フローを素早く確認したかった。
- **AIの活用**: Google Antigravity内のGeminiを活用して構築を進めました。ただし、AIに丸投げするのではなく、現場の課題整理・仕様決定・挙動確認・修正判断はすべて人間が行い、AIを実装の強力な補助として活用しています。

## 3. 主な機能

### 患者側フォーム
用途に合わせて4種類の予約フォームを用意しています。
- 新規予約・再予約
- 予約変更
- 初回カウンセリング予約
- ご紹介専用予約

### 希望日時選択
- 第1希望〜第3希望まで選択可能
- 「午前」「午後」「終日」または15分単位での詳細な時間指定
- **柔軟な条件進行**: 第1希望と第2希望が別日で、かつ両方が「午前」「午後」「終日」などの広めの時間帯指定であれば、第3希望が未入力でも次へ進める仕様
- 第3希望未入力時のエラーを防ぐnullガード機能

### お客様情報入力
- お名前（漢字）、ふりがな、電話番号
- ご紹介専用予約のみ「ご紹介者名」を追加
- 全項目に対するリアルタイムの入力バリデーションとエラーメッセージ表示
- すべての項目が正しく入力されている場合のみ「次へ進む」ボタンが有効化される仕組み

### 管理画面
- **予約申請一覧・ステータス管理**: 届いた予約希望の確認とステータス（完了など）の変更
- **カレンダー管理・不定休設定**: 任意の日にちを休診日として設定・解除
- **時間帯ブロック**: 15分単位での予約不可枠（ブロック）の設定と解除
- **患者・ブロック管理**: ステータス変更に伴う変更回数カウントや悪質な予約のブロック判定
- **案内用フォーム一覧**: 各フォームへのリンク一覧
- **同期ステータス表示**: リアルタイムでの同期状態の可視化
- **デモデータ管理**: デモ用の自動リセット機能（毎日深夜0時）

## 4. 技術構成

初期版では、まず動くデモを短期間で形にすることを優先したため、HTML / CSS / Vanilla JavaScriptを中心とした軽量な構成になっています。

| 領域 | 技術スタック |
| --- | --- |
| フロントエンド | HTML / CSS / Vanilla JavaScript |
| バックエンド | Node.js / Express |
| データ保存 | Firebase (Cloud Firestore) |
| ホスティング | Render Web Service |
| ソース管理 | GitHub |
| デモ運用 | デモデータ自動削除 / 手動リセット |

## 6. データ管理

- 予約データ、休診日設定、時間帯ブロック、顧客データなどはすべて **Firebase (Cloud Firestore)** に保存しています。
- Render Postgres等のRDBは使用していません。
- Render内のローカルファイル保存には依存しないステートレスな構成です。
- 本システムは**デモ用として運用**しており、実在の個人情報や本番データは入力しない運用としています。
- 毎日深夜0時に自動で設定データがリセットされる仕様が組み込まれています。

## 8. セキュリティ・注意点

- **実在データの入力禁止**: 現在はデモ公開環境のため、実在する患者情報や電話番号などの個人情報は絶対に入力しないでください。
- **セキュリティ強化の必要性**: 本番運用に移行する前には、より強固な認証、詳細な権限管理、監査ログ管理などのセキュリティ強化が必須です。
- **秘匿情報の管理**: Firebaseのサービスアカウントキー（`firebase-key.json`）や、`.env` ファイルなどのAPIキー・秘密情報は絶対にGitHub上に公開（コミット）しないでください。

## 9. 今後の展開

現在の軽量構成（Vanilla JavaScript版）で仕様の妥当性が確認できたため、今後は以下のステップで開発を進める予定です。

- **仕様の基準化**: 現在の修正済みHTML版の挙動を正しい仕様（正）として扱います。
- **モダン技術への移行**: 今後、Next.js / TypeScriptを用いた構成へ再構築する予定です。
- **コンポーネント化と型定義**: 既存のHTMLをそのまま移植するのではなく、文言、分岐ロジック、バリデーションルール、LINE送信文面などをしっかりと抽出して型定義化（TypeScript）します。
- **患者側フォームの共通化**: 4つのフォームは共通コンポーネントとして再利用性を高めつつ、フォームごとに異なる質問や分岐については個別管理できる設計にします。
- **管理画面の再構成**: 患者側フォームの移行完了後、管理画面についても段階的にNext.js / TypeScriptへ再構成していきます。

## 10. AI活用について

本プロジェクトは、**Google Antigravity内のGemini**を活用して作成されました。
また、ChatGPTも併用し、仕様の整理や指示書の作成、説明資料の骨子作成などに活用しています。
AIを活用していますが、「すべてをAIに丸投げして作らせた」わけではありません。現場が抱える課題の整理、仕様の妥当性判断、実際の挙動確認、および修正方針の決定などは人間が行い、AIは強力な「実装の補助・壁打ち相手」として活用しながらシステムを構築しました。
